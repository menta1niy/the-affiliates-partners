# The Affiliates Partners — повторный аудит лида и прав менеджеров

Дата: 2026-11-26. Базовая production-версия до этого изменения: `09164a8ab1045afd3203816035a5c704227314b3`.

## Решение по модели полномочий

По явному требованию владельца **все активные роли `owner`, `admin` и `staff` обладают глобальными операционными полномочиями**. Принадлежность лида агентству, назначенный менеджер, `source` и `manager_id` остаются учётными атрибутами, но не ограничивают чтение или рабочие действия этих доверенных ролей. Обычные `lead`/`referrer` не приобретают права администрирования.

Исключения: нельзя модерировать учётную запись владельца или собственную учётную запись, изменить собственную роль/менеджера, назначить `owner` и изменить Telegram ID; защищены финансовые инварианты, аудит, шифрование СБП. Это паритет **операционной админ-панели**, а не доступ к серверным секретам и SSH.

| Возможность | owner | admin | staff | lead |
|---|---|---|---|---|
| Список всех зарегистрированных, поиск, карточка, журнал | Да | Да | Да | Нет |
| Одобрение, отклонение, блокировка, разблокировка другого пользователя | Да | Да | Да | Нет |
| Роль admin/staff/lead/referrer, назначение менеджера и исправление источника | Да | Да | Да | Нет |
| Приглашения агентства и рефералы, отзыв приглашения, коды блогера | Да | Да | Да | Собственная реферальная ссылка, если активен и дал согласие |
| Каталог офферов: создание, удаление, логотип, текст, ставка, срок, этапы, URL, доступность | Да | Да | Да | Только чтение опубликованного |
| Назначение офферов, массовое назначение/предпросмотр, ручные статусы | Да | Да | Да | Только личное выполнение |
| Очередь этапов и МФО, решение, вложения и история | Да | Да | Да | Только личные события/файлы |
| Финансовые начисления, суммы, резерв, история заявок и платежей | Да | Да | Да | Только личные начисления и вывод |
| Реквизиты СБП ожидающих выплат, confirm/reject/paid | Да | Да | Да | Только подача заявки на вывод |
| Блогерский кабинет: регистрация, ставки, фиксы, проверка и оплата | Да | Да | Да | Нет |

## Жизненный цикл участника

1. **Вход:** подписанный Telegram Mini App initData; бот выдаёт /start и запрашивает свой контакт. Проверка сервера зависит от `PARTNERS_REQUIRE_TELEGRAM_CONTACT=true`, настройка текущего работающего процесса Aeza независимо проверена.
2. **Регистрация:** требуется consent/privacy/terms и `adult_confirmed=true`. Регистрация с открытым доступом активирует пользователя сразу; проверенная реферальная ссылка закрепляет оригинальный источник, самоприглашение запрещено. Дата рождения, ИНН, ФИО и опрос кредитных продуктов в текущем MVP отсутствуют намеренно. Подтверждение 18 лет основано на чекбоксе, а не документах.
3. **Каталог:** все действующие опубликованные предложения видны, назначенные персональные статусы не подменяются доступными публичными офферами; МФО требует ручного запроса менеджеру.
4. **Этапы:** участник может отметить любой настроенный этап без обязательного вложения либо приложить до 10 МБ файла произвольного формата. Дубли подтверждённых этапов и одновременные ожидающие заявки блокируются. Вложение хранится на сервере в исходном виде; legacy Fernet-вложения читаются старым ключом; API ограничивает доступ. Это не подтверждает банковскую конверсию или начисление.
5. **Модерация:** менеджер просматривает события/файлы, подтверждает/отклоняет этап, событие и решение отражаются в истории/аудите. Действия по офферам не создают автоматически финансы.
6. **Начисление:** уполномоченный менеджер вручную добавляет подтверждённое начисление с уникальным источником, комиссия и задержка отдельно отражаются в статистике.
7. **Вывод:** участник отправляет сумму, телефон СБП и банк; Fernet реквизиты доступны менеджерам только пока выплата в состоянии pending/confirmed, просмотр аудируется. Следующий переход статуса требует уникального платёжного идентификатора, после paid/rejected реквизиты очищаются.
8. **Реферальная выплата:** 15% вознаграждения активному lead/referrer при фактическом paid приглашённого участника, не раньше. Пример из регрессионного HTTP QA: 101 ₽ → 1515 копеек; SQLite и PostgreSQL17 прошли, повторы paid возвращают 409. Реферальные и блогерские программы разделены.

## Что не регулируется админкой

Не существует отдельной графической страницы общих server settings. Из UI нельзя редактировать env-переменные, ключи шифрования, SSH и PostgreSQL, SSL/Nginx, Telegram webhook/menu, базовую формулу 15%, настоящие банковские подтверждения, аудит задним числом, реальный Telegram ID пользователя, уже выплаченные записи/уникальные платёжные идентификаторы. Это намеренные серверные/финансовые ограничения, а не отсутствие кнопки у staff. Возможность менять юридические страницы и их утверждённые редакции также не предоставлена из панели.

## Проверки

- SQLite: 197/197 тестов каталога/регистрации/действий лида/ролей/финансов/рефералов/массовых назначений пройдены после актуализации устаревших проверок. Ещё 61/61 адресных тестов менеджеров, финансовых карточек и ограничений пройдены.
- Playwright Chromium: три теста на роли и мобильные размеры 320, 375, 390 и 430 px, включая фактические frontend действия staff по управлению ролями и блогером, пройдены.
- Реальный изолированный PostgreSQL17: регистрация по реферальной ссылке, 101 ₽ paid, 15,15 ₽ рефереру, запись в журнале, повторный paid 409 — пройдено. Дополнительный PG17 набор выявлял несоответствия старых ожиданий restricted staff и удалённых endpoint, не реальные изменения production.
- JS `node --check`, Python `compileall`, `git diff --check` — пройдены.
- Работающий сервер Aeza до релиза: `PARTNERS_REQUIRE_TELEGRAM_CONTACT=true`. Не проверялся живой Telegram WebView на устройстве и не создавались тестовые финансовые записи на production.

## Операционные риски и ограничения

- Глобальный доступ staff/admin и расшифровка СБП существенно повышают последствия компрометации менеджера. Активный статус и роль, аудит, запрет изменения собственного/владельца профиля, уникальность выплат и финансовый ledger сохраняются; для высокого финансового оборота рекомендован отдельный принцип `maker-checker` и регулярная проверка журналов.
- Приложенные файлы намеренно могут быть произвольными и нешифрованными: контролировать квоты/сроки хранения/антивирусную обработку и не требовать приватные документы через этот механизм.
- Возраст подтверждается заявлением пользователя, без документальной проверки; контакт Telegram сервер требует только при включённой настройке (на текущем Aeza включена).
- Нет полной живой e2e проверки через iPhone Telegram и доставки уведомлений; браузерные тесты и HTTP не заменяют этот этап.
