# The Affiliates Partners — Design Audit, этап 1

**Дата:** 2026-11-16
**Локальный исходный коммит:** `d3269686ce33b02b585dab6969b8cf9c0ef567a8`
**Ветка:** `feature/green-theme-20261114`
**Область:** исключительно локальный frontend. Сервер, backend, БД, production и API не менялись.

## 1. Принятые дизайн-решения

- Визуальное направление: **Luxury Monochrome Fintech × Frosted White Glass × Soft White Luminescence × Precision Dashboard**.
- Основные поверхности — `#080909`, `#0D0E10`, `#131416`, `#1B1D20`; акцент **белый**, а не зелёный. Тёмный текст на главной белой CTA.
- Стекло — тонкий полупрозрачный белый слой преимущественно на функциональных карточках; не размывать весь экран. Белое свечение — избирательное, слабое, предпочтительно по верхним кромкам и у главного действия.
- Крупные editorial-заголовки сочетаются с компактной рабочей плотностью. Избегать цветных декоративных акцентов, «криптобиржевого» вида и фиктивных графиков.
- Mobile-first для Telegram WebView, затем responsive desktop с боковой навигацией там, где достаточно места.
- Не трогать регистрацию, авторизацию, права ролей, финансы, CRM, схемы данных, существующие API и поведение backend. Кнопки должны продолжать выполнять реальные действия.
- Примерные параметры из мастер-ТЗ (палитра, размеры, opacity, blur) становятся **кандидатами** для этапа 2, а не готовыми применёнными правилами.

## 2. Фактическая архитектура frontend

Это **vanilla HTML/CSS/JavaScript**, не React. Никакой framework-migration для редизайна не требуется.

| Файл | Роль и важные особенности |
| --- | --- |
| `web/index.html` | Статическая структура кабинета: hero, авторизация, регистрация, статус/источник, офферы, legacy CRM-блоки, приглашения, профиль |
| `web/app.js` | Telegram initData, API-fetch, отображение состояний, офферов и статистики, отправка регистрации, копирование ссылки |
| `web/admin/index.html` | Админ-хедер, 4 KPI, вкладки, очереди и таблицы, форма приглашений, диалог профиля |
| `web/admin/admin.js` | Все данные админки, динамические таблицы/действия, каталог в создаваемом JS-диалоге, профиль лида, назначения, статусы, журнал |
| `web/style.css` | Единая таблица стилей обоих приложений, мобильные правила, Telegram safe area, последовательные переопределения темы |
| `web/telegram-layout.js` | Telegram viewport/safe area/fullscreen и цвета системных поверхностей |

Сборка статического релиза строго перечисляет эти **6 файлов**; см. `tools/build_static_release.py`. CSS, HTML и JS используются непосредственно браузером. Оба HTML-документа подключают Telegram WebApp SDK.

Текущий общий CSS содержит **несколько конфликтующих поколений дизайна**: первоначальная зелёная палитра, последующие Unbounded/«glass» overrides, а затем финальные `--green-*` overrides. Его необходимо привести к одной системе токенов на этапе 2, без потери селекторов и состояний.

Дополнительно сейчас:

- `#051F20` жёстко указан в обоих `meta[name=theme-color]`, `telegram-layout.js`, `web/app.js` и `web/admin/admin.js`: смена CSS без этих *UI-only* цветов оставит несогласованное оформление Telegram.
- Шрифт заголовков сейчас `Unbounded`; body изначально `Inter`, затем наследуется `Unbounded`. Переход к Plus Jakarta Sans требует проверки длины русских строк, цифровых колонок и fallback при недоступном Google Fonts.
- Диалог `#participant-detail` имеет **inline зелёные стили** в HTML; `#mvp-catalog-dialog` получает inline стили из JS. Для новой темы нельзя полагаться только на общие правила CSS.
- Значительная часть разметки и интерактивных кнопок генерируется в JS; сохранить DOM-ID и JS-event wiring при изменении внешней оболочки.
- Существующие CSS-классы `.btn`, `.panel`, `.metric`, `.offer-item`, `.admin-tabs`, `.table-wrap`, `.toolbar`, `.pill`, `.message` — исходные точки будущих общих компонентов.

## 3. Карта экранов и фактических действий

### 3.1 Кабинет участника `/partners/`

| Состояние/блок | Сейчас | Действие / источники данных | Визуальный план без новых API |
| --- | --- | --- | --- |
| Вход через Telegram | Hero + `#connect`, если отсутствует initData | `/api/session`; ссылка на официальный бот | Премиальный Hero + чёткий экран авторизации |
| Регистрация | `#register-panel` + согласие | `/api/register` после signed initData; ожидает ручного одобрения | Одношаговая стеклянная карточка с primary CTA |
| Pending/rejected/blocked | Status hero и карточки | Текущая `session.status` | Явная нейтральная статусная метка и понятный empty-state; не показывать запрещённые действия |
| Активный аккаунт | `#account`, персональное приветствие, status/source | `/api/session` | Крупный Hero и компактная идентификация |
| Мои офферы | `#offers`, dynamic JS article per offer | `/api/mvp/overview` при `open_registration=true`; другой legacy путь при выключенном флаге | Монолитные стеклянные offer cards с суммой, холдом, целью, статусом, инструкцией и ссылкой |
| Статистика | Сейчас текст «Всего назначено / В работе / Завершено» | `statistics.total`, `statistics.in_progress`, `statistics.completed` | KPI из реального payload, никаких выдуманных цифр |
| Приглашения | `#referral-panel` | `/api/invitations/referral` + копирование | Компактная вспомогательная секция, только когда сервер разрешил |
| Профиль | Имя, Telegram ID, внутренний ID, роль, статус, переход в админку | Данные `session.user` | Стеклянная компактная карточка |
| Legacy CRM | Скрываемые JS секции `task-history`, `crm-state`; task reporting | `/api/tasks`, `/api/tasks/report`, `/api/lead-view` | Сохранить backward-compatible DOM/обработку; не добавлять CRM в standalone MVP |

Статусы назначения: `assigned`, `in_progress`, `submitted`, `completed`, `rejected`. Последние два — **ручные отметки**, не банковские выплаты. `payout_rub` — ставка по условиям оффера.

**Уточнение KPI:** в нынешнем `/api/mvp/overview` `in_progress` включает и `in_progress`, и `submitted`. Разделение на «В работе» и «На проверке» возможно только путём **подсчёта уже загруженного массива `offers` по `stage`**, если этот массив полон и корректен. Иначе необходимо оставить три достоверных показателя, а не выводить фиктивную четвёртую метрику.

**Уточнение навигации:** сейчас кабинет — одна длинная страница без нативных «Главная / Мои офферы / Статистика / Профиль» экранов. При проектировании навигации следует предпочесть локальные якоря/переключение UI-контейнеров, сохраняя существующий fetch-state и доступность; не вводить новые backend endpoints.

### 3.2 Админка `/partners/admin/`

| Раздел/компонент | Фактически существует | Действия, которые нельзя потерять |
| --- | --- | --- |
| Общие показатели | 4 карточки: total / pending / active / blocked | `/api/admin/dashboard`, реальные счётчики |
| Заявки | вкладка `pending` и таблица | Одобрить, отклонить (с причиной), блокировать с подтверждением, открыть карточку |
| Участники | вкладка `users`, поиск, статус/роль, постраничность | `/api/admin/users`, `/api/admin/participant`, смена ролей/менеджеров, ограниченные owner-only исправления источника |
| Профиль участника | `#participant-detail` dialog | Просмотр ID, scope/атрибуции, назначений, ручных статусов и заметок; назначить/убрать оффер, сохранить статус, одобрить pending, аудит |
| Каталог офферов | **не отдельная вкладка**: динамическая кнопка + `#mvp-catalog-dialog` | `/api/admin/mvp/catalog`, owner-only создание/редактирование/активность; каталог доступен owner/admin для чтения |
| Приглашения | вкладка `invitations`, форма и таблица | Создать, скопировать ссылку, отозвать, просмотреть |
| Журнал | вкладка `audit` | `/api/admin/audit` |
| Обновить | `#reload` | Повторная загрузка, не терять состояние и ошибки |

**Уточнение навигации:** «Обзор» сейчас представлен **KPI перед вкладками**, но отдельной вкладки нет. «Каталог офферов» — отдельный динамический диалог, а не `data-panel`. В целевом дизайне их можно представить как отдельные визуальные области, однако изменение маршрутизации/структуры следует выполнять только без нарушения существующих действий.

**Важное разграничение:** owner и admin могут читать каталог, **изменять общий каталог может только owner**. Текущая админка показывает кнопку каталога обеим ролям, но диалог содержит форму редактирования; это UX-несоответствие, которое необходимо учитывать при стилизации, не расширяя серверные права.

**Другие текущие UI-ограничения:** часть административных операций использует `window.prompt`/`window.confirm` (решения, роли, атрибуция, отзыв). Нельзя заменять их нарисованными неработающими формами. На данном редизайне улучшать представление только при сохранении точной логики и проверок.

## 4. Целевые композиционные решения

### Участник, mobile-first

1. Верхняя компактная панель с брендом; Telegram safe-area соблюдается.
2. Тёмный editorial Hero: **«ТВОИ ОФФЕРЫ. / ТВОИ РЕЗУЛЬТАТЫ.»**; акцентная белая мягко светящаяся CTA ведёт к действующему разделу офферов.
3. Статус аккаунта/ожидания модерации — явно и без отображения лишней функциональности.
4. KPI компактными стеклянными карточками; количество достоверных показателей соответствует payload.
5. Главный список назначенных офферов, затем вспомогательные приглашения/профиль.
6. На мобильном — компактная навигация по существующим областям, без обязательного нового URL или API.

### Администратор, mobile-first и desktop

1. Компактный брендированный header; desktop допускает sidebar, mobile — удобные вкладки/меню.
2. Hero: **«УПРАВЛЯЙ. / КОНТРОЛИРУЙ.»**, но не отнимать экранную высоту у очереди заявок.
3. Четыре реальные KPI в сетке 2×2 mobile и до четырёх в строку desktop.
4. Быстрый переход к заявкам и участникам; каталог как полноценная удобная область при сохранении тех же API.
5. Приоритет: карточка участника и функции назначения/статуса должны быть пригодны для работы одной рукой.
6. Журнал и приглашения — вспомогательные разделы, не главный декоративный фокус.

### Общая визуальная иерархия

- Фон почти чёрный, основные панели графитовые, стекло только выборочно.
- Белый — единственный декоративный акцент; primary CTA белая/молочная с тёмным текстом.
- Небольшое белое свечение по верхним кромкам и вокруг единственного главного действия в секции.
- Не использовать корону, логотипы или графику конкурента; абстрактная форма может быть реализована лёгким CSS/SVG без тяжёлых 3D-ресурсов.
- Для текстовых/функциональных ошибок разрешать семантические отличия, но не декоративные разноцветные панели.

## 5. Аудит responsive, доступности и UI-рисков

| Наблюдение | Влияние | Требование следующих этапов |
| --- | --- | --- |
| На узких экранах административные таблицы остаются таблицами с горизонтальной прокруткой | Частые действия неудобны на телефоне | Семантические мобильные карточки при сохранении таблицы desktop |
| `#participant-detail` ограничен `max-height:85vh` и inline отступами | Клавиатура Telegram может перекрывать поля | Адаптивные размеры от viewport, безопасные отступы и прокрутка внутри |
| Каталог создаётся как отдельный JS dialog, форма с `input[type=text]` для инструкции | Длинные инструкции неудобны | Стилизовать динамически создаваемые поля, продумать многострочный ввод только на UI-этапе |
| Таблица поиска/фильтров desktop и mobile наследует несколько CSS overrides | Непредсказуемые размеры и контрасты | Одна система layout и breakpoint |
| `--green-*` и `#051F20` встречаются в JS/HTML/CSS | Смена CSS не заменит цвет шапки Telegram и диалогов | Синхронно заменить только UI-константы в соответствующем этапе |
| В CSS используются `backdrop-filter` и `prefers-reduced-transparency` | Слабые смартфоны / accessibility | Ограничить количество blur-панелей и дать непрозрачный fallback |
| Есть `prefers-reduced-motion`, `:focus-visible`, `aria-live` | Существующая база доступности | Сохранить и улучшать, не ломать |
| На странице активного лида присутствует `#owner-preview` hidden, без исполняемого preview-модуля | Ненужный placeholder | Не выводить demo в production; убрать только после проверки тестовых селекторов |
| UI состоит из узких и широких русскоязычных текстов, Telegram ID и ссылок | Высокий риск переполнения | Проверить 320/375/390/430/768/1024/1440 px, длинные имена, большие суммы, ошибки |

## 6. Реальные UI/API контракты, которые требуется сохранить

- Telegram initData передаётся в каждом POST запросе через `/partners/api...`; проверка подписи выполняется сервером.
- `/api/session`, `/api/register`, `/api/mvp/overview`.
- `/api/admin/dashboard`, `/api/admin/users`, `/api/admin/participant`, `/api/admin/decision`, `/api/admin/assign`, `/api/admin/audit`, `/api/admin/attribution`.
- `/api/admin/mvp/catalog`, `/api/admin/mvp/offer`, `/api/admin/mvp/assignment`.
- Приглашения и legacy CRM endpoints остаются существующими и должны продолжать работать, даже если их блоки скрыты в standalone-режиме.
- UI не может самостоятельно подтверждать банк, `paid`, `credited` или баланс. `completed` относится только к ручному статусу.
- Сохранить отсутствие фальшивых данных, обработку denied/empty/loading/error и изоляцию по ролям.

## 7. Карта риска для будущего редизайна

**P0 — не допустить регрессии:** signed Telegram session, новая регистрация/consent, owner/admin/staff permissions, одобрение, назначение/снятие оффера, сохранение статуса, строгая изоляция данных.

**P1 — обязательная usability-проверка:** длинные офферы/ссылки, 320px mobile, Telegram safe-area, клавиатура над диалогом, читабельность opacity-стекла, заметные focus/error/disabled, сворачиваемые условия, поиск/пагинация.

**P2 — косметика:** свечение, текстура, иллюстрация Hero, анимация. Не должны блокировать выпуск или нарушать скорость.

## 8. Граница этапов и критерии завершения

**Этап 1 (текущий):** аудит исходного интерфейса, подтверждённая карта экранов, выявленные несоответствия ТЗ и технические ограничения. **Никаких изменений поведения UI, CSS, backend или production.**

**Этап 2 (отдельная команда пользователя):** подготовить монолитную дизайн-систему токенов/шрифта/стекла/свечения, установить правила fallback и состояния. Не начинать до разрешения на следующий этап.

**Этапы 3–7:** общий набор компонентов, кабинет участника, админка, responsive QA, регрессия/controlled release — каждый по отдельному явному продолжению.

**Верификация этапа 1:** прочитаны 6 файлов frontend, пути взаимодействий и проверены существующие browser-сценарии в тестах; исходный Git чист на старте аудита. Изменён **только этот документ**, без выполнения деплоя.
