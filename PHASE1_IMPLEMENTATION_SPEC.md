# Этап 1 — техническое задание и критерии приёмки

## Источники и границы
Рабочий проект — `TheAffiliates-Partners-Concept`; использовать существующую ветку и сохранять незакоммиченные файлы. Основной сайт и CRM — самостоятельные приложения: не изменять их серверы, БД и деплой в рамках интеграции без отдельно подтверждённого безопасного контракта. Не объявлять общую БД с CRM без подтверждения её действительной схемы, доступа и владения данными.

## Идентификация
Telegram WebApp `initData` валидируется только сервером: HMAC, срок действия, отсутствие дублирующихся ключей, целочисленный положительный Telegram ID. Пользователь определён по Telegram ID; username — изменяемый атрибут профиля. Номер привязывается только при передаче собственного Telegram-контакта из бота; повторный контакт не сбрасывает статус. Существующие одобренные аккаунты и номера сохраняются. Авторизация возвращает фактический профиль и состояние из одной БД бота/API. Администратор определяется только проверенным Telegram ID владельца, а не username.

## Пользовательский путь
Новый пользователь: `/start` → собственный контакт → сохранение телефона и username → заявка pending → уведомление владельца → approve/reject. Повторный `/start` отражает фактический статус и не просит контакт у зарегистрированного пользователя. Повторная заявка для rejected — явное действие. Mini App различает загрузку, отсутствие регистрации, ожидание, отклонение, активный аккаунт и ошибку авторизации. Нельзя отображать демопрофиль/выдуманные деньги при сетевой ошибке.

## Администрирование
Только серверно подтверждённый владелец видит административный раздел и может просматривать заявки, одобрять/отклонять партнёров, редактировать офферы, изменять их публикацию и статусы. Каждый admin endpoint проверяет подписанный initData и ID владельца. Запись в БД должна быть атомарной, устойчивой к повторным вызовам; уведомления не должны откатывать успешное одобрение при недоступности Telegram.

## Бизнес-данные
Партнёры видят только одобренные опубликованные офферы. Настоящие клики, целевые действия, холд, выплаты и статистика должны подключаться лишь к документированному достоверному источнику; до подключения отображаются корректные пустые состояния и явный статус «не подключено», а не поддельные показатели. Партнёрские ссылки не генерировать фиктивно.

## Деплой
Все правки локально → тесты/сборка → GitHub. Публичную публикацию и изменения рабочего окружения — только по авторизации. Обновления фронтенда/API/бота проверяются отдельно; не трогать основной сайт. Не вносить секреты и реальные SQLite-данные в Git.

## Проверки
Регистрация, повторный `/start`, forwarded contact, дедупликация номера, неадминский 403, владелец без строки в `partners`, статусы и идемпотентность, сохранение данных после перезапуска, отсутствие демоданных, компиляция и production build. Отдельно зафиксировать непроверенные сценарии на реальном Telegram/iPhone и наличие интеграции с CRM.
